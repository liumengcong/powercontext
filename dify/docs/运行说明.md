# 运行说明

## 1. 创意与完整玩法

玩家输入一件离谱失物，例如“会打嗝的月亮”“忘记下班的闹钟”。AI 柜员登记它的特殊习性，安排三道荒诞办事窗口。每次选择 A/B/C 会改变默契值并获得纪念章；三关后出现三种结局之一。再次打开同一 Workflow、保留同一存档口令，柜员可以找回物品、进度和上一回合真实输入，继续故事。

六种事件按物品及局数产生可复现的三关组合。三种结局分别对应高、中、低默契值；选择没有唯一“正确答案”。“档案”可查看收藏册，“重开”清空当前物品但保留收藏册和审计历史。最多展示最近 20 个收藏、20 次操作，保存最近 4 个写请求回执以吸收短时重试。

正式入口是 Dify Workflow 的测试/发布页面或 Workflow API，不需要独立网页。每次执行输入 `player_key`、`action`、`message`。存档口令只用于虚构游戏，请生成独立随机值，不要使用真实账号密码。

## 3. Dify 流程

```text
开始
 → 输入校验与 UUID 请求号
 → HTTP /v1/prepare：读取 PowerContext，计算下一状态但不写记忆
 → 校验响应并提取真实历史上下文
 → Dify LLM：依照真实状态生成柜员旁白
 → 生成 JSON 保存请求
 → HTTP /v1/commit：验证签名/版本，保存 Memory 和原始 Source
 → 输出旁白、由程序生成的准确档案、记忆回执
 → 结束
```

模型失败时不会进入 commit，所以不推进关卡。HTTP 重试复用同一请求 JSON；同一签名票据近期重复提交，返回之前的回执，不重复加分。两个并发预备操作只有一个可更新当前版本，另一个返回 409，需重新运行。票据 15 分钟有效。

`00_` DSL 用规则旁白替代 LLM，仅用于诊断；`01_` 是正式 AI 作品。建议先导入 `00_` 检查网络，再导入 `01_`、选择模型。两个文件没有互相依赖，也没有知识库需要重新绑定。

## 4. 原生安装

在本项目 `dify` 目录运行：

```bash
python3.12 -m venv .venv
.venv/bin/python -m pip install -c requirements.lock -r requirements.txt
.venv/bin/python scripts/setup.py
.venv/bin/python -m uvicorn backend.app:app --host 127.0.0.1 --port 8787 --workers 1 --env-file .env
```

Windows 可使用 Python 3.12 的 `py -3.12` 建环境，并将 `.venv/bin/python` 换为 `.venv\Scripts\python.exe`；本项目未在 Windows 实测。Linux 与 Mac 可用上面的原生命令。

初始化脚本只在 `.env` 不存在时生成随机 `BACKEND_TOKEN`，不覆盖现有配置。`data/powercontext.db` 和调度数据库由官方 SDK 首次启动自动创建。无需导入初始数据库，无需预置玩家。

就绪检查：

```bash
curl http://127.0.0.1:8787/healthz
```

返回 `{"status":"ready","powercontext":"1.2.0",...}` 后，再发业务请求。`/healthz` 只证明服务就绪，不能替代游戏记忆验收。

## 5. Docker 后端方案

前提：已安装可用的 Docker Compose。

```bash
python3.12 scripts/setup.py
docker compose up -d --build --wait
docker compose logs --tail=50
```

该 Compose 只启动配套后端；Dify 仍用参赛者自己的 Cloud 或自部署实例。服务端数据在 `lost-found-data` 命名卷中。停止时用 `docker compose down`，不删除卷；重启沿用相同 `.env` 和命名卷。

## 6. Dify Cloud 网络与长期部署

Dify Cloud 请求来自云端，不能访问作者电脑上的 localhost。它必须使用公网可达的 HTTPS 后端地址。后端只需约 1 核 CPU、512 MB—1 GB 内存和可写磁盘；这是轻量项目的起步配置建议，并非经过压测的保证。需要能从 PyPI 安装锁定依赖。

长期运行可在现有 Linux 服务器上按原生方式或 Compose 启动，再将域名 HTTPS 反向代理到服务器的 `127.0.0.1:8787`。例如使用已有的 Caddy：

```caddy
game.example.com {
    reverse_proxy 127.0.0.1:8787
}
```

将 `game.example.com` 换为自己的域名；配置 DNS、有效 TLS 证书和相应入站网络。不要直接使用占位域名。服务器应挂载持久化磁盘，重建容器后保留数据。平台费用和域名由部署者自行安排，本项目不依赖某家付费服务。

自己联调可使用 `临时公网联调_Mac.command`，它优先复用已安装的 cloudflared；需要安装时从官方 Release 下载固定版本 2026.11.0，校验 SHA-256 后解压。下载使用 HTTP/1.1、超时和断点续传，避免本机曾出现的 HTTP/2 下载中断。隧道传输使用 auto 自动协商协议；网络中断后若旧隧道失效，重新运行会分配新地址，需同步 Dify 两个应用的 BACKEND_BASE_URL。2026-11-17 已完成一次真实公网健康检查与未授权请求拦截验证，见 `evidence/tunnel_connectivity.json`；这不替代 Dify Cloud 与模型验收。终端关闭、电脑休眠、地址改变后 Cloud 调用可能失败。不要把临时地址作为唯一可复现性保障。

自部署 Dify 若与后端同网，可使用该部署实际能访问的服务名或网络地址；Docker 容器内的 localhost 指向容器自己。需要相应调整 Dify 的网络/HTTP 节点策略，不能通过关闭 TLS 校验来掩盖地址或证书问题。

## 8. 检查与证据

```bash
.venv/bin/python -m pip install -c requirements.lock -r requirements-dev.txt
PYTHONPATH=. .venv/bin/python -m pytest tests -q
.venv/bin/python scripts/verify_backend.py
.venv/bin/python scripts/verify_dify.py
```

前两类使用真实 PowerContext；`verify_backend.py` 启动真实 HTTP 服务，使用临时测试数据库，停止后重启并验证恢复。它不使用 Dify 或 LLM，报告中明确标记为 false。

`verify_dify.py` 只通过真实已发布的 Dify Workflow API 运行。缺少 Key 会直接退出；失败会记录 failed；成功才会生成 passed 记录。需要在线后端、可用模型、有效应用 Key，可能消耗模型额度。它不能自动替你导入应用、选择模型或伪造执行追踪截图。

## 9. 实际记忆与原始记录

`player_key` 的 SHA-256 作为 Scope 创建的幂等键的一部分，每个玩家拥有官方创建的独立 Scope。原始口令不作为 Memory 文本持久化，也不返回给其他玩家。

当前游戏整体状态保存在该 Scope 的 `game-state` Memory Entry；每次写操作产生 Memory 修订。读取与回访使用同一 Scope 的最新状态，不依赖 Dify 会话历史。

玩家输入、计算后的上下文与旁白保存为官方 Content Source，`source_id` 记录在该操作回执中；`/v1/inspect` 使用官方 Record API 回查这些 Source，并返回 Memory citation。该追溯方式是通过回执里的 Source ID 关联，不声称给 Memory Entry 配置了额外的原生 source lineage。

程序只通过 SDK 操作这些数据，没有用自建数据库冒充 PowerContext。模型只写叙事文本；档案、选项、积分及结局均由规则生成并附在回复后，避免模型幻觉改变存档。

## 10. 已知限制

- 目前未在参赛者自己的 Dify Cloud 中完成导入和全链路实测；交付的本地证据不替代该步骤。
- 本地 Docker 不可用，Dockerfile/Compose 未构建实测；优先使用已测试的原生启动方式。
- 本服务按单进程、单 worker 设计，串行处理存档写入，适合小型演示；不声明多副本部署或大规模并发能力。
- 最近 4 个写请求有去重回执，超出窗口的旧请求不承诺永久去重；正常新回合使用新请求 UUID。
- “重开”保留历史修订和收藏，便于审计，不是隐私删除接口。只输入虚构游戏内容。
- 相同存档口令表示同一游戏身份；知道口令的人可读取该虚构存档。项目没有替代真人账号系统。
- 模型生成文本具有随机性。验收主要核对事实、结构、玩家选择与记忆复用，不要求唯一固定文案。
- 若进程恰好在 Source capture 后、Memory commit 前中断，可能留下未关联的原始 Source；不会据此推进游戏。再次操作须以 Memory 回执和最新版本为准。
