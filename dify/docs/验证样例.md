# 验证样例

正式验收使用 `01_离谱失物招领处_AI正式版.yml`。无模型自检文件仅用于先排查网络。

## 前置条件与恢复初始状态

- 后端已就绪，PowerContext 1.2.0 使用持久化数据目录。
- Dify 已导入正式版 DSL、填写公网 HTTPS 地址及 Secret、选择可用聊天模型并发布。
- 每次独立验收使用一个新的随机 `player_key`，例如 `judge-20261116-ab72`。样例值只是虚构存档口令，不是真实用户密码。
- 开始前在后端调用 `/v1/inspect`，该玩家应为 `revision: 0`、`current: null`。不要求作者已有数据库。
- “重开”保留收藏册和历史；要获得全新验收初始状态，请换新的口令。无需删除数据库。

## 样例一：从寄存到结局的完整游戏

所有步骤保持相同的 player_key，每步都重新点击 Dify 运行，**不是把上次回答复制进下一次输入**。

| 步骤 | action | message | 预期表现 |
| --- | --- | --- | --- |
| 1 | 寄存 | 会打嗝的月亮 | AI 柜员登记该物品，展示第一道窗口的 A/B/C、档案号和 0/3 进度。记忆版本 0 → 1。 |
| 2 | A | 请记得我给月亮买了芋泥啵啵 | 第一关完成，获得对应纪念章，展示第二关。保存这条真实输入。版本 1 → 2。 |
| 3 | 回访 | 我开了新一次运行，回来看看 | 找回同一物品和 1/3 进度。传给 LLM 的 callback 包含“芋泥啵啵”和上次选择，旁白自然回应至少一个历史细节。版本 2 → 2。 |
| 4 | B | 这次请盖一个不太认真的章 | 第二关完成，展示第三关，版本 2 → 3。 |
| 5 | C | 我宣布今天是星期八 | 第三关完成，显示 3/3、一种明确结局、三枚纪念章，收藏册包含这件物品。版本 3 → 4。 |
| 6 | 档案 | 留空 | 恢复同一物品、结局及收藏。版本 4 → 4。 |

每道窗口的 A/B/C 和得分由服务端固定规则决定。由于事件组合取决于物品名和局数，不要求所有物品出现同一套窗口。AI 文本没有唯一标准答案；应保持物品、关卡、历史选择及结局一致，不替玩家做下一步选择。

## 样例二：跨 Dify 运行与后端重启

1. 完成样例一的第 2 步，保存 `memory_proof`。
2. 关闭这一次 Dify 运行结果；重新进入应用或打开另一个新的运行页面。
3. 仍使用同一 player_key，选择“回访”。检查第二关和“芋泥啵啵”的历史内容仍能进入 AI 上下文；不手工提供旧对话。
4. 停止后端，然后使用同一个 `.env` 和同一 `DATA_DIR` 重新启动。
5. 再次“回访”，物品、选择、版本不变，证明来源是持久化 PowerContext，而不是当前进程的字典或 Dify 临时历史。

本地交付的 `backend_actual_run.json` 已包含真实 HTTP 服务停止和重启后的检查；参赛者仍应补充自己 Cloud 环境中的对应执行记录。

## 样例三：玩家隔离

换一个全新 player_key，action 选择“档案”。应显示尚未寄存和记忆版本 0，不能出现另一个玩家的月亮、输入或收藏册。切回原口令后原档案应仍存在。

## 样例四：模型失败不提前推进

1. 在测试副本中暂时选择一个不可用模型配置，执行合法下一回合。
2. Dify LLM 节点应失败，后面的 `/v1/commit` 不执行。
3. 修复模型，先“回访”确认进度没有因上一次失败而变化。
4. 再执行合法选项，确认只推进一次。

不要在正式应用里长时间保留故障模型。该样例由工作流执行顺序和后端只读 prepare 保证，本地测试覆盖了“prepare 不写 Memory”；**真实 Cloud 的模型失败追踪仍需账号内补证**。

## 样例五：异常与重试

- 无服务口令或错误服务口令：HTTP 401。
- player_key 格式不符、寄存内容为空、重复寄存：422 和明确中文提示。
- 已结案后再选 A/B/C：不推进，提示回访或重开。
- 同一签名提交票据近期重放：回执 `replayed: true`，Memory 版本不增加。
- 两个基于相同旧版本的不同准备请求同时提交：第二个得到 409，不能覆盖先完成的玩家选择。
- 修改票据内容或签名：拒绝；不修改 Memory。

## 提交证据清单

1. 导入后的 Dify 工作流全貌，能看见 LLM 和两次 HTTP 调用。
2. 正式版一次“寄存”的完整执行详情；模型节点、提交节点成功。
3. 新运行“回访”的执行详情，读取结果的 callback 包含上一回合真实输入。
4. 最终结局和 `memory_proof`。
5. `scripts/verify_dify.py` 生成的 `evidence/dify_live_acceptance.json`，且 status 为 passed。
6. 使用的 Dify Cloud 可见版本信息（若平台未显示，记录“不显示”及实测日期）、模型名、供应商插件版本、后端版本和长期入口/重建方式。

检查截图和日志不含 API Key 或服务口令。只有本地规则旁白、单元检查或 YAML 语法检查，不足以代表完整 Dify + AI + PowerContext 验收。
